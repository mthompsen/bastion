## 2. Item 1: OCSF and ECS views, Detection Finding export (`9e5e56c`)

`bastion/normalize/` holds two pure functions of one event, `to_ocsf` and `to_ecs`. They read
the event's fields and never change them, and nothing in the engine calls them.

| Kind of record | OCSF 1.9.0 class (activity) | ECS 9.5.0 `event.category` / `event.type` |
|:-|:-|:-|
| Sysmon 1, Security 4688, auditd exec | Process Activity 1007 (Launch) | process / start |
| Sysmon 5, Security 4689 | Process Activity 1007 (Terminate) | process / end |
| Sysmon 10 | Process Activity 1007 (Open) | process / access |
| Sysmon 8 | Process Activity 1007 (Inject) | process / change |
| Sysmon 3, Security 5156 | Network Activity 4001 (Open) | network / connection, start |
| Security 4624, 4625, 4648 | Authentication 3002 (Logon) | authentication / start |
| Security 4634, 4647 | Authentication 3002 (Logoff) | authentication / end |
| Security 4768, 4769, 4771 | Authentication 3002 (Authentication Ticket, Service Ticket Request, Preauth) | authentication / start |
| Sysmon 11; 23, 26 | File System Activity 1001 (Create; Delete) | file / creation; deletion |
| Sysmon 12, 14 (keys) | Registry Key Activity 201001 (Create, Delete, Rename) | registry / creation, deletion, change |
| Sysmon 12, 13 (values) | Registry Value Activity 201002 (Set, Delete) | registry / change, deletion |
| anything else | Base Event 0 | `event.kind: event` only |

Rules the views follow, so that no view is silently lossy and nothing is invented:

- Every field a view has no place for is kept under its source name: OCSF `unmapped`, ECS
  `bastion.unmapped` (a custom field set, as ECS advises). The source record is OCSF
  `raw_data` and ECS `event.original`.
- Enumerations Bastion cannot decide are Unknown (`0`) or Other (`99`, with the source value
  as the caption), never guessed. Network direction comes only from Sysmon `Initiated` or the
  5156 `Direction` code; otherwise Unknown.
- A value a class requires is never invented. An event without a timestamp has no `time` and
  is labelled `bastion:no-timestamp`; a process with neither a pid nor a guid is not emitted
  (its fields stay in `unmapped`); a record that names no host has no `device`. Such views are
  not schema valid, and say why.
- Security 4688 names the new process `NewProcessId` and its creator `ProcessId`; the views
  keep them apart (a test pins this).
- The OCSF `host` profile is applied (`metadata.profiles: ["host"]`): Bastion reads host logs,
  and without it Network Activity, Authentication and Base Event have no `device` or `actor`.

**Detection Finding.** `bastion report` now also writes `findings.ocsf.json`: one OCSF 1.9.0
Detection Finding (2004, activity Create, status New) per detection. Severity is the Sigma
level (informational 1 to critical 5); `finding_info.analytic` is the rule (id, title, Sigma
release); `finding_info.attacks` has one entry per technique and tactic, with the ATT&CK
version; the evidence holds the matched fields and the acting process, file, registry or
endpoint objects of the event's view. The finding's time is the event's time, and its uid is
a hash of the rule id and the raw record, so the export is deterministic.

**Validation.** The tests validate every view and finding against the OCSF 1.9.0 JSON Schema
of its class (with the `host` profile) and every ECS document against the ECS 9.5.0 field list
and categorization allowed values. Both are small attributed fixtures in
`tests/fixtures/standards/` (rebuilt by `scripts/build_standards_fixtures.py`), so the tests
run offline. `jsonschema` was added as a dev dependency for this. Over all events of the two
committed EVTX samples and the Windows goodware log set (evtx-baseline v0.8.5), counts only:

- The two samples: 11 events, every OCSF view and ECS document valid.
- Goodware: 224,797 events. Every ECS document is valid. 222,417 OCSF views are valid: Base
  Event 120,660, Registry Value 64,606, Process Activity 7,141, Registry Key 26,047, File
  System 3,868, Network 51, Authentication 44. The other 2,380 are Process Activity views
  without `actor`, which the class requires; that is the only schema error. Bastion leaves
  `actor` out when the record names no acting process, by design (above). Reading the code,
  the likely source is process termination (Sysmon 5, Security 4689), whose record names no
  parent; Security 4689 does name the subject user, which the view could carry as
  `actor.user`. The breakdown by event id was not measured: that run was stopped for low
  memory. Left for a later milestone; it changes no detection.

## 3. Item 2: standards data with drift reporting (`b4e7fe9`, tests `58bc026`)

`bastion/standards/` loads each source, resolves its ATT&CK ids against the pinned 20.1
release (revoked ids followed through `revoked-by`, as rule tags are), and reports the drift:
the release the mapping declares (or that it declares none), ids revoked, deprecated or unknown
in 20.1, and how many live techniques it leaves unmapped. `bastion standards fetch` downloads
the D3FEND, CTID and CAR files into `data/standards/` (gitignored) and checks the digests; a
source not fetched is reported as not fetched and fails nothing.

Drift against ATT&CK 20.1 (706 live enterprise techniques and sub-techniques), from
`bastion standards status`:

| Source | Declares | Ids | Live | Revoked (followed) | Deprecated | Unknown | Techniques mapped | Live techniques unmapped | Rows left out |
|:-|:-|-:|-:|-:|-:|-:|-:|-:|:-|
| D3FEND 1.6.0 | not stated | 326 | 311 | 14 | 1 | 0 | 323 | 383 | 2,238 ICS, 624 SPARTA |
| CTID 800-53 | 16.1, **older than 20.1** | 470 | 454 | 15 | 0 | 1 | 466 | 240 | 96 `non_mappable` |
| MITRE CAR | not stated | 122 | 117 | 5 | 0 | 0 | 120 | 586 | none |

- The CTID warning Mason expected is there: `CTID ATT&CK to NIST 800-53 maps ATT&CK 16.1,
  older than the pinned 20.1`.
- D3FEND's relations are inferred through digital artifacts (a countermeasure hardens or
  analyzes an artifact the technique uses); each entry names that path. Mapping only; no
  automated response.
- CSF 2.0: seven Bastion functions labelled with CSF outcomes (DE.CM-01, DE.CM-03, DE.CM-09,
  DE.AE-02, DE.AE-03, DE.AE-06, DE.AE-07, ID.IM-02), the CSF text quoted exactly. The
  assignment is Bastion's assertion, and the file and the status output say so.
- DeTT&CT: `bastion standards dettect FILE` reads data-source-administration (1.1) and
  technique-administration (1.2) files, reports another type or format version as unsupported
  rather than rejecting it, checks technique ids against 20.1 and data source names against
  its data components (106 live), and reports the scores the file states. Bastion computes no
  DeTT&CT score.
- `bastion standards technique T1003.001` lists the D3FEND countermeasures, 800-53 controls and
  CAR analytics for one technique, with the drift warnings of each source.

## 4. Item 3: SARIF and Navigator (`b00e79d`)

**SARIF** (additive; no property renamed or removed). `runs[0].properties.bastion` carries:
the scan's pins and the bench pins, the standards pins, the tagged coverage with numerator,
denominator and basis ("enterprise techniques tagged by at least one loaded rule, any status,
hunting class included; rule-only evidence, not validated detection": it is not the claimed
coverage of section 4, which excludes the hunting class), the OCSF findings file, and where
ladder levels come from. Each rule and result carries `ladderLevels` for its techniques.

A scan has no evidence ladder of its own; it comes from a bench run. `bastion report
--bench-summary bench/results/<run>/summary.json` names the run. Without it, `ladderLevels` is
empty and the run properties say no ladder level is stated. With it, the run properties record
the bench run, its pins, and whether they match the scan's Sigma and ATT&CK pins.

**Navigator.** `bastion report` writes `layers.navigator.json`, a list of layers in format 4.5:
techniques tagged by loaded rules (score: number of rules), detections in the scanned log
(score: number of detections), and with a bench summary the evidence ladder (score 0 none to
4 held-out-proven, legend per rung; no rung is drawn in a success green). Every layer is
marked lossy in its description and metadata (`lossy: true` with the reason: one score per
technique cannot carry tri-state results, bases, intervals or evidence), names its basis, and
lists the pins. The ladder layer says so when the bench run used other pins than the scan.
