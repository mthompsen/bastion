**Why the estimate was wrong.** The plan assumed that once the files parsed, the commands in
them would reach the rules. Three things stop that, and none is a parse defect. First, Splunk
ships each audit record type as its own file and most of these datasets include one file, so
a dataset is SYSCALL-only, PROCTITLE-only or EXECVE-only, while each SigmaHQ auditd rule reads
one specific record type. A fully parsed SYSCALL-only dataset still has nothing for an EXECVE
rule. Second, `proctitle` is not mapped to any Sigma field (deliberately, in B2), so the
PROCTITLE-only captures stay invisible to `process_creation` rules. Third, 8 captures record
an invocation no rule covers. The plan counted "a Linux alerting rule exists for the
technique" as recoverable; that was the overestimate.

**Rule class.** The headline counts alerting-class rules only. Of the rules cited above, five
are hunting class (status experimental): Potential Abuse of Linux Magic System Request Key,
System Info Discovery via Sysinfo Syscall, Linux Setuid Capability Set on a Binary via Setcap
Utility, New Cron File Created and Shadow File Read Attempt. Every other cited rule is
alerting class.

**What B3 can still recover honestly.** F1 (next section) is the only parser defect here, and
it affects `auditd_path_sysrq`; but the rule that then fires there is hunting class, so F1
does not recover that capture for the headline. A `proctitle` to `CommandLine` mapping would
expose `chattr_i` and `dd_overwrite` to alerting `process_creation` rules (Remove Immutable
File Attribute, DD File Overwrite), and the `setuid` chmod runs to Setuid and Setgid
(alerting); that is a field-mapping lever with its own benchmark, not part of F1. Mapping the
numeric `syscall` to its name (per `arch`) makes the sysinfo rule evaluable on `lsmod_new`,
but that rule is hunting class. The rest need new rules (B4) or data the datasets do not
contain.

**Note on tri-state.** In an EXECVE record, a missing `a3` when `argc` is 3 is a definite
`no_match`, not `not_evaluable`. The xclip case is reported as not evaluable today. Recorded
for the F1 work rather than changed here.

**The other 9 held-out no-alert captures** (line 129 set only): T1562.004 `disable_firewall`
is now detected (lever b's tag resolution); `T1068/.../auth.log` has no rule matching its
syslog content; T1033 `whoami` is SYSCALL-only against an EXECVE rule; T1053.003
`cron_file_audited` and T1548.003 `sudoers_access` are PATH-only against `file_event` rules
that read `TargetFilename` (a PATH `name` to `TargetFilename` mapping is a B3 candidate; New
Cron File Created is hunting class, Persistence Via Sudoers.d Files is alerting);
T1098.004 `nopasswd` has no rule for the behaviour and its label looks questionable; T1489

for them; T1546.004 `unix_shell_mod_config` has PATH records naming only parent directories,
not the files the rule lists; T1547.006 `modprobe` has no rule (the rule is insmod only).

Method: for each capture, every Linux rule tagged to its live technique (parent-aware) was
evaluated per event and per field predicate, reporting only states, field presence and counts
(`diag24.py`, `perfield.py`, outside the repo). The rule class column was added after a
review: the first pass did not separate hunting-class rules. No log values were read into
this report, except one PATH name (a directory) that a script's error message printed. No
rule, tag or label change came from it; the auditd field-mapping lever (section 6) was
motivated by it, which the contamination log records.
