## 2. Store (`727fc11`)

`bastion/store/` follows the B0 store decision (section 10.2): standard library `sqlite3`,
WAL mode, one file per workspace, JSON in TEXT columns, a busy timeout so the API and a job
worker can write the same file. The schema is versioned with `PRAGMA user_version` and
migrated forward on open; a store from a newer Bastion is refused, not rewritten. The file is
`%LOCALAPPDATA%\bastion\store.sqlite3` on Windows and `$XDG_DATA_HOME/bastion/store.sqlite3`
(default `~/.local/share`) elsewhere, or `BASTION_STORE`; never inside the repository.

| Table | Holds | Key |
|:-|:-|:-|
| `scans` | one row per scan: file, platform, events, rules loaded, pins, and the scan result without its detections (not-evaluable and outside-source counts, filters, tag resolution, tagged coverage as covered of total) | uid |
| `detections` | rule, level, host, event time, techniques, matched fields, the event itself | row id; indexed by scan, finding uid, rule |
| `triage`, `triage_history` | status (new, reviewed, false_positive, needs_follow_up) and note; every change kept | the finding uid |
| `bench_runs` | a run's `summary.json`, its commit, evaluation hash and pins | run name |
| `filter_documents` | each filter document in `filters/`: id, title, path, sha256, text | filter id |
| `tag_disputes` | the entries of `docs/tag-disputes.md` (origin `ledger`) and disputes added through the API (origin `local`); status open, reported upstream, resolved, withdrawn | id; unique rule and tag |
| `jobs` (schema 2, `8640d26`) | section 4 | uid |

Decisions inside the scope, so that the store cannot change a detection:

- Triage is keyed on the finding uid (a hash of the rule id and the raw record, the same id
  as the OCSF finding of B5), not on a row id, so a decision survives a rescan of the same log
  and the deletion of a scan.
- Filter documents are records. The engine keeps loading filters from `filters/`; a filter
  in the store is never applied. The store mirrors the directory on each sync.
- A tag dispute is a ledger entry and never retags a rule. The ledger file stays the record of
  origin: on sync, an entry from it takes the ledger's status; local entries are left alone.
- A bench run is recorded at summary level only. No capture event is stored or served, so the
  API exposes nothing of the held-out split beyond what `summary.json` already commits.

## 3. API (`af0e7b3`)

`bastion/api/` is a FastAPI app. The contract is
[`docs/api/openapi.json`](../api/openapi.json), written by `scripts/build_openapi.py`; a test
fails when the committed file differs from what the code serves. FastAPI is pinned to
`>=0.165,<0.166` because the generated document depends on its version. The interactive docs
pages are off (they load scripts from a CDN); the contract is served at `/api/openapi.json`.

| Method and path | Purpose |
|:-|:-|
| `GET /api/health`, `GET /api/pins` | store path and schema; bench and standards pins |
| `POST /api/sync` | record the repository's bench runs, filter documents and dispute ledger |
| `GET /api/scans`, `GET`/`DELETE /api/scans/{uid}` | scan history and one scan's summary |
| `GET /api/detections` | page of detections with triage state; filters: scan, level, rule, host, triage |
| `GET /api/detections/{id}` | one detection with its event and the raw, OCSF and ECS views |
| `GET /api/detections/{id}/finding` | the detection as an OCSF 1.9.0 Detection Finding |
| `PUT /api/triage/{finding_uid}`, `GET .../history` | set triage status and note; the history |
| `GET /api/bench-runs`, `GET /api/bench-runs/{name}` | bench run records and one summary |
| `GET /api/filters`, `GET /api/filters/{id}` | filter documents and one document's text |
| `GET`/`POST /api/tag-disputes`, `PATCH /api/tag-disputes/{id}` | disputes; add one; change status or note |
| `GET`/`POST /api/jobs`, `GET /api/jobs/{id}`, `POST /api/jobs/{id}/cancel` | section 4 |

Bound to 127.0.0.1 only: the host is fixed in code and `bastion gui` has no host option. A
loopback bind is not enough for an API a browser can reach, so every request is also checked:

- the `Host` header must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding gets 403);
- a write (POST, PUT, PATCH, DELETE) with an `Origin` other than those, or a `Sec-Fetch-Site`
  other than same-origin, gets 403;
- a write must send `application/json` (an HTML form cannot), else 415;
- no CORS is configured, so a cross-origin preflight is not answered.

Tests cover each of these.

## 4. Jobs (`8640d26`)

A job is a row in the store with a kind (scan or bench), its parameters, a status (queued,
running, done, failed, cancelled), progress, attempts, the worker's process id, the error if
any, and the result: the scan uid or the bench run name, which is also recorded in the store.

- **One at a time.** The dispatcher in the `bastion gui` process starts the oldest queued job
  in its own worker process (`python -m bastion.jobs`) only when no job is running, as the
  one-bench-at-a-time rule asks. The API stays responsive during a three-hour bench run.
- **Progress.** A bench job reports captures done of total and the current corpus, counting
  captures whose outcome is reused; a scan job reports events read and its file (the total is
  known only at the end).
- **Cancel.** A queued job is cancelled at once. A running job is asked to stop: a bench
  worker checks between captures, a scan worker every 1,000 events. A worker that has not
  stopped 30 seconds after the request is terminated and the job marked cancelled.
- **Resume after restart.** On start, a running job whose worker process is gone goes back to
  queued (or to cancelled, if its cancel was requested). A bench job keeps the run name it was
  given when queued (default `gui-<date>-<id>`), so the rerun reuses every capture outcome
  already written; a scan job reads its file again. Two gaps in the runner's resume were
  closed: a truncated last line in `outcomes.jsonl` (a worker killed mid-write) is skipped
  and ended, instead of failing the resume and corrupting the next line.
- **Where results go.** A bench job writes to `bench-results/` beside the store, never to the
  repository's `bench/results/`, whose `LATEST` the CI budget gate reads.
- **What changed outside `bastion/jobs/`.** `bench/runner.py` gained the progress and stop
  hooks and the resume fixes; `cli.py`'s scan pipeline gained an event-stream hook and its
  bench configuration a repository and results root. Neither file is among the modules the
  bench hashes as evaluation logic, and the CLI commands behave as before.

The API accepts only the parameters in the contract: a scan job takes a file path and an
optional platform; a bench job takes a run name, splits, suites, an event cap, baseline sets
and channels. Rules, ATT&CK and corpus locations are the CLI defaults.

## 5. `bastion gui` (`87536b8`)

`bastion gui [--port 8765] [--store FILE] [--open/--no-open]` opens the store, records the
repository's bench runs, filter documents and dispute ledger, queues again any job a previous
stop left running, starts the dispatcher, opens the browser, and serves on
`http://127.0.0.1:<port>/` until interrupted. `/` is a placeholder page saying the GUI comes in
B7 and pointing to the contract.

Smoke run on this machine: the server listened on `127.0.0.1:8799` only; a request with
`Host: evil.example` got 403; a scan job on the committed EVTX sample ran in a worker process
to `done` with 6 of 6 events and 3 detections, the same as `examples/output/`.

## 6. Notes

- The Starlette test client warns that its `httpx` transport is deprecated. Tests pass; the
  warning is left for the next dependency update rather than adding a package now.
- A worker's liveness is judged by its process id. A reused process id after a reboot could
  keep a job running until it is cancelled; acceptable for a local tool, stated here.
- The store is a plain file under the user's profile; it holds raw event records of scanned
  logs. It is not encrypted.

## 7. No detection change: `b6` against `b5`

One bench run, `b6`, at `87536b8` (the last code commit of B6, which includes the B5 actor
fix), compared capture by capture with `b5`:

- 1,418 captures in each; 0 differ in any recorded key (rules fired with their counts and
  classes, filtered, not evaluable with the missing fields, outside source).
- Every summary block is identical, and so are the bench pins. The evaluation source hash is
  the same, `3ed2cf82dd17`: no module the bench treats as evaluation logic changed.
- The headline figures are those of `b5` and `b4c-c`: test-split technique recall 136 of 512,
  validated coverage 84 of 244; benign replay 500 alerts over 31.23 host-days (16.01 per
  host-day, budget 20); evidence ladder held-out-proven 84, sample-proven 26, fixture-proven
  2, rule-only 269, none 325.

`bench/results/LATEST` is now `b6`.
