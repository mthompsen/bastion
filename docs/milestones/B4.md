## Working rules

- **Test captures are never inspected** for rule development. Their outcomes are read only as
  aggregate benchmark numbers.
- **Dev captures may be read for rule development** (lever a). Only the fields a rule keys on
  are printed, from the one dev capture a rule is developed on, and each such read is listed in
  the contamination log. This narrows B3's context hygiene rule to what development requires.
- **Labels are never changed** to fit a rule.
- **Every filter carries a written justification** and its recall cost on dev, held-out and
  regression.

## 1. Lever b: Linux keyword noise

**What the specification says.** Sigma specification 2.1.0, "Keywords search"
(sigma-specification `ba9251a`, `specification/sigma-rules-specification.md`), reads:

> Contrary to the Field Usage, It's a matter of searching for keywords across an entire event.
> They are built by using a list under a search-identifiers.

A plain list is an OR; `'|all':` makes it an AND. "Values" (same file) are case-insensitive
strings with `*` and `?` wildcards. The specification does not say whether a keyword must be a
whole token or may be a substring, and it does not restrict the search to any field.

Bastion searches a keyword case-insensitively as a substring of the event's raw text and field
values. That is a reading of "across an entire event" the specification does not contradict,
so Bastion does not deviate from the specification. Under Mason's rule, the noise is rule
quality: it gets a filter document and draft upstream text, and the matcher is not changed.

**Measured** (own-lab benign background at `b3-xml`; benign data, not held out). Per record,
the branch is attributed by which of the rule's keyword lists the record text contains, and
the command is the EXECVE `a0` basename:

| Branch | Firings | Commands (`a0`) |
|:-|-:|:-|
| `init and initselection` | 290 | sh 95, logger 80, ln 30, tee 20, python3 20, sed 10, and 5 each of setpriv, mount, umount, mktemp, cat, awk, rm |
| `shutdowncmd` | 20 | systemd-update-utmp 10, shutdown 5 (the real `shutdown -P now`), python3 5 |

None of the 290 init-branch firings is init or telinit. The dev attack_data auditd captures
have no firing of this rule. No other keyword-based Linux rule fires on the own-lab background;
the other background firings come from rules on named fields (for example Creation Of An User
Account, 170).

**Change.** One filter document,
`filters/linux/lnx_auditd_system_shutdown_reboot_init_branch.yml`, with its justification in the
file. It suppresses a detection of this rule only when the event's command is not init or
telinit and none of the four shutdown command keywords appears. It is scoped to `product:
linux` without `service: auditd`, so it is evaluated on the merged audit event (which carries
`a0` and every record's text). Per-record evaluation would let a SYSCALL record, which has no
`a0`, satisfy "not init" and hide a real `init 0`.

A unit test (`tests/test_filters.py`) runs the shipped file over synthetic events:

- `init 0`, `telinit 6`, `shutdown -P now` and `systemctl reboot` are kept;
- `sh` and `logger` lines that merely contain "init" and a digit are suppressed.

**Draft upstream issue for Mason's review** (not filed):

> **Title:** System Shutdown/Reboot - Linux (4cb57c2f): init branch matches any audit record
> containing "init" and a 0 or 6
>
> `lnx_auditd_system_shutdown_reboot.yml` detects the init branch with two keyword lists,
> `init: ['init', 'telinit']` and `initselection: [0, 6]`, in `execve and (shutdowncmd or
> (init and initselection))`. Keyword search runs across the whole event, so on a backend
> that matches keywords as substrings, any EXECVE record whose text contains "init" (for
> example "initialised", "initrd", "--init") and any 0 or 6 (record serial, timestamp,
> argument) matches. On a benign lab host, 290 of 310 matches came through this branch, none
> of them an init or telinit invocation. Suggested change: express the branch on the command
> fields, for example
> `init_cmd: {a0|endswith: ['/init', '/telinit']}` or `a0: ['init', 'telinit']`, together with
> `a1: ['0', '6']`, and keep the keyword list for the shutdown commands only. Real
> `init 0` and `telinit 6` still match, because the EXECVE record carries `a0` and `a1`.

**Before and after** (`b3-xml` to `b4-b`, commit `ff3bc6d`):

| Measure | `b3-xml` | `b4-b` |
|:-|-:|-:|
| Frozen 130: headline / strict / any firing | 38 / 33 / 76 | 38 / 33 / 76 |
| Expanded test, 512 captures in both: headline / strict / any | 124 / 105 / 283 | 124 / 105 / 283 |
| Windows goodware per host-day, overall / medium and above (budget 20) | 15.82 / 13.80 | 15.82 / 13.80 |
| Own-lab benign background per host-day, overall / medium and above | 55.45 / 15.45 | 32.70 / 15.45 |
| Own-lab background alerts | 707 | 417 |

The filter suppressed 302 detections across the run:

- 290 on the own-lab benign background, 58 on each of the 5 hosts. The rule drops from 310 to
  20 there; the 20 left are the `shutdowncmd` branch, including the real `shutdown -P now`.
- 12 on two dev captures labelled T1053.006 and T1569.003, 6 each. Neither is a shutdown
  technique, so these were false positives too.

Medium-and-above is unchanged because the rule is informational. The own-lab overall rate
falls by 41 percent and is still above 20; the next largest source is Creation Of An User
Account (170, medium), which matches on named fields and is not keyword noise.

**Recall cost: none measured.** The headline, strict and any-firing counts are identical on
both test sets. The one T1529 capture (attack_data `auditd_path_sysrq`, test) had no firing
of this rule before or after. The one test capture where the rule fires (a T1552.004 capture)
keeps all 13 of its firings; it was not opened, only its counts were compared.

## 3. Lever c, part 1: process lineage (run `b4-c1`)

`src/bastion/process_tree.py` builds process lineage within one scan; `engine.scan` runs it on
every event before any rule reads that event.

- **Recording.** Each process start is recorded, keyed by host and process id (and Sysmon's
  `ProcessGuid`): Sysmon 1 (Windows and Linux), Security 4688, and a merged auditd event with
  an EXECVE record. A process is forgotten at its termination (Sysmon 5, Security 4689).
- **Filling.** A later start that names a recorded process as its parent gains `ParentImage`,
  `ParentCommandLine` and `ParentUser` from the parent's `Image`, `CommandLine` and `User`,
  only where the event lacks them. Nothing is overwritten.

Why: at `b3-xml`, `ParentImage` (86,362 rule-event pairs), `ParentCommandLine` (38,313) and
`ParentUser` (3,933) are among the fields most often behind not_evaluable. Security 4688 has no
parent command line, and before Windows 10 no parent image; a merged auditd exec names only
`ppid`.

Limits, stated in the module: a parent must appear before its child, and a parent that started
before the capture is unknown. A reused process id whose termination was not logged can name
the wrong parent. That is a precision risk, measured by the goodware replay.

Tests: `tests/test_process_tree.py`, with synthetic events. The README canary is unchanged.

Before and after (`b4-c1`, against `b4-d`): pending the run.

## 4. Lever c, part 2: correlation (run `b4-c2`)

**Engine.** `src/bastion/sigma/correlation.py` is ported from Citadel M2. The source is
Citadel's `citadel/core/sigma/correlation.py`, last changed in Citadel commit `12a0fed` and read
at Citadel HEAD `ff50c75`; it is MIT licensed and by the same author. Nothing was run in, or
written to, the Citadel repository. The port keeps Citadel ADR 0008:

- A correlation file is the correlation plus its building blocks.
- The rule loader skips correlation files, so a building block can never alert on its own.
- `generate: true` is refused.
- Types `event_count`, `value_count`, `temporal` and `temporal_ordered` are evaluated; the
  other three types the specification defines are recorded as unsupported.
- Windows slide for lower bounds and tumble for upper bounds.
- `pid` groups with more than one `Image` are reported as collisions, not findings.

Bastion's version differs in four ways:

- It is **streaming**. A `Correlator` sees each event once inside `engine.scan` and keeps only
  the events a correlation's inputs matched.
- **There are no run windows** (those are Citadel's). The bound is the rule's `timespan`.
- **Naive timestamps are read as UTC**, so one group may mix sources with and without a zone.
- **Techniques come from constituent rules only** (START_PROMPT section 6 lever 5). A
  correlation's own tags speak for building blocks in its file; a tag beyond the tags of the
  rules it names by id is dropped.

`bastion scan` prints correlation findings, and the bench counts each finding as one firing of
the correlation's id.

**Content.** No document in the pinned SigmaHQ trees is a correlation, so the content is
local, in `rules/`:

| Rule | Technique | STP | Developed on (dev only) | Status |
|:-|:-|-:|:-|:-|
| Failed Logons For Many Accounts From One Source (4625, 10 or more distinct `TargetUserName` per `Computer` and `IpAddress` in 5 minutes) | T1110.003 | 4 | attack_data T1110.003 `purplesharp_remote_spray_xml`, `purplesharp_valid_users_ntlm_xml`, `purplesharp_multiple_users_from_process_xml` | experimental |
| Kerberos Authentication Failures For Many Accounts From One Source (4771 `0x18` or 4768 `0x6`, same grouping and bound) | T1110.003 | 4 | attack_data T1110.003 `purplesharp_invalid_users_kerberos_xml` | experimental |
| Several Host Discovery Commands From One Parent (Citadel M2, unchanged logic) | T1033 | 4 | Citadel own-lab captures (dev-only corpus), in Citadel | experimental |

Dev reads for these rules went through a helper that refuses any capture whose manifest split
is not `dev`. It printed only the named fields of matching events (`TargetUserName`,
`IpAddress`, `WorkstationName`, `LogonType`, `Status`, `SubStatus`, `ProcessName`,
`Computer`; five events from one capture, three from another) and event counts by channel and
EventID for four captures. The B1 correlation candidates (Kerberos spray, short-lived task)
were held-out captures and were not used.

**Status.**

- The goodware replay's Security log (win2022-evtx, 22,085 events) holds no 4625, 4768 or
  4771. So zero goodware findings is no evidence that the two Windows correlations are quiet
  on benign data.
- Following Mason's rule for the Linux local rules (stay experimental while benign evidence is
  empty), both stay `experimental`, so hunting class, and cannot move the headline in this run.
  Promoting them to `test` is Mason's decision.
- On all 156 dev Windows captures, only the four T1110.003 spray captures fire, once each.

## 5. Lever a: new local rules for writable gaps (run `b4-a`)

- ATT&CK places it on a Windows or Linux host;
